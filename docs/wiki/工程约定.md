# Trip 工程约定

[项目地图](index.md) · [协作指引](../../AGENTS.md)

这里整理已有实现与用户明确决定中对后续工作有约束的部分，不将所有历史代码写法都视为标准。业务规则由各业务专题维护，以下约定不授权存量代码全量迁移。

这些是当前代表性路径。局部功能应先定位相应封装，不能只根据目录名称推断某项行为已经具备事务、权限或重试保证。

## 分层职责与依赖边界

除场景入口外，当前源码还可按下列分层理解职责。这是职责视图，不表示严格线性层次；Agent 编排、工具回调、应用对基础设施等具体依赖方向要沿实际调用链确认。

| 分层 | 职责与边界 | 代表源码 |
| --- | --- | --- |
| HTTP 与工具接入 | `controller` 与 `agent/tool` 适配参数与可信上下文后，业务流程和需要共享的业务规则委托应用服务，工具的已有轻量外部查询可以直接使用 Client；不承载供应商协议与存储 | [ConversationController](../../fons4ai-trip-agent-service/src/main/java/com/fons/cloud/ai/trip/controller/ConversationController.java)、[ItinerarySearchTools](../../fons4ai-trip-agent-service/src/main/java/com/fons/cloud/ai/trip/agent/tool/ItinerarySearchTools.java) |

| 业务模型与领域数据 | `domain` 的 entity 表达业务模型，DomainService 承担表级 CRUD 与领域数据读取 | [ChatMessageDomainService](../../fons4ai-trip-agent-service/src/main/java/com/fons/cloud/ai/trip/domain/service/ChatMessageDomainService.java) |

这是对现状的描述，不强制目录迁移：应用层可继续使用现有基础设施，需要隔离时按实际需要引入接口，不预设委托层。简单表不强制补建 DomainService，应用层局部直用 Mapper（如发布快照表 TravelOrderItineraryPlanMapper）不升级为全局规则。结果与异常的既有约定不变，见[身份、结果与权限](#身份结果与权限)。

模型配置与调用是能力而非独立分层，SDK 原生记忆、结构化业务偏好与静态提示词规则也各自职责不同：模型装配见 [框架接入](framework-integration.md#模型如何按协议装配)，偏好与原生记忆的边界见 [差旅业务](travel-business.md#结构化差旅偏好与原生记忆)。

## 身份、结果与权限

- 用户身份来自服务端登录态；候选、规划、审核、页面使用可信用户与根业务会话。不要退回 SDK 子会话 ID，也不要以 Trace 是否开启决定业务归属。依据：[TripRuntimeContext](../../fons4ai-trip-agent-service/src/main/java/com/fons/cloud/ai/trip/infrastructure/agent/TripRuntimeContext.java)。
- 普通业务返回沿用 `R` 和既有结果码；工具的业务失败、外部调用异常和空结果分别处理，不把它们统一改成“查询成功但无数据”。既有直接返回 `R` 的业务流程不因异常体系迁移而改为抛异常。
- 主动抛出的异常使用 Fons4Cloud 的 `BsException` 体系，并按请求校验、身份认证、业务状态、系统故障或外部调用选择分类。普通失败 `Result` 必须明确分类和模块，已有 `ExceptionCode` 保留其分类和模块；不可把成功码或取消状态当作异常码。Trip 当前复用 [TripExceptions](../../fons4ai-trip-agent-service/src/main/java/com/fons/cloud/ai/trip/common/exception/TripExceptions.java) 构造常见错误定义；保留已有错误码、安全说明和必要的原因。JUC 取消信号等具有控制语义的异常按原协议传播。
- 天气、资讯、签证和途牛供应商的请求及响应协议失败使用外部异常；配置缺失和内部存储问题按系统故障处理。为保持既有错误码，Trip 的外部异常暂沿用原系统错误码，其分类和模块是 `EXTERNAL` / `TRIP`；框架原有 `ResultCode` 的定义不变。工具和审核层分别维持既有结果映射及覆盖缺口，不把外部失败视为成功空结果。
- 当前 Trip 解析出的依赖不含 `fons4cloud-common-web`；不能仅凭框架中存在全局处理器就认定 Trip 已启用。HTTP 和 SSE 对新异常的实际输出须分别验证，SSE 流建立前后的错误处理不能等同于普通 JSON 接口。
- `run_ended` 是应用对外的分段收口通知；过程事件、任务清单完成、HTTP 断开与模型文本不能替代权威结果。详见 [会话执行](conversation.md)。
- 工具许可、差旅单审批和方案审核分别建模；提示词中的“确认后执行”与 SDK ASK 规则不是同一种强制约束。
- 密钥不进入 Wiki、模型提示词、候选快照或完整错误回显。需要说明配置时写属性名、用途与来源，不复制运行配置值。

## 事务与并发

复合业务修改沿用应用服务已有的 `TransactionTemplate` 事务组织，检查保存结果；不要仅凭 `@Service` 认定跨调用原子执行。审批恢复使用条件更新及可信持有者字段，重要异常不能被吞掉后宣布成功。依据：[ConversationApplicationService](../../fons4ai-trip-agent-service/src/main/java/com/fons/cloud/ai/trip/application/conversation/ConversationApplicationService.java)。

同一会话的执行占用分别由 Redis 租约和数据库条件更新保护；释放要匹配当前 Run，实际退出前不交还执行权。业务写入的旧执行隔离与完整故障接管不是当前租约方案的已有保证。

用户明确要求：需要锁协调复合状态时优先 JUC 原子类或 Lock，不新增以方法入参为监视器的 `synchronized`。线程安全容器不自动保证跨字段、跨存储的操作原子性；需要时参考框架已实现的生命周期边界。

## 可读性与演进

为字段、对外方法和关键业务边界补必要注释，解释可信来源、状态限制、事务交接与例外，而不逐行复述代码。命名、异常和日志优先沿用目标模块约定，不为小改动增加新的委托层、调度器或基础设施。

用户明确要求实现保持轻量、可读：围绕已确认场景复用现有 CRUD，不为尚未发生的来源、仲裁、同步等问题预设功能。页面和工具表达同一业务操作时共用服务，新增类型或抽象必须能对应当前实际职责。

用户于 2026-10-28 明确要求：`if` / `else` 分支必须使用大括号，即使分支只有一条语句也不能省略；`switch` 必须提供 `default`，明确处理未支持的值，不能静默忽略未知分支。新增和修改代码遵守该约定，不因此进行全仓历史代码迁移。

固定业务状态、操作、来源和目录选项优先使用独立枚举统一映射，不在数据类或调用点散落字符串类型码。字段说明使用 JavaDoc；record 字段逐项分行，并以完整 `@param` 说明含义、空值、时间口径及关联约束，不自动添加运行期字段描述注解。受 SDK 或既有协议约束的编码字符串保留在边界，由业务枚举统一校验，不为形式上的强类型破坏 Schema 与实际报文的一致性。

模型输出用于提出参数和方案；客观金额、归属、候选引用、审核与发布资格由可信数据和服务判断。具体约束见 [行程规划](itinerary-planning.md)，避免把提示词要求误写成代码保证。
