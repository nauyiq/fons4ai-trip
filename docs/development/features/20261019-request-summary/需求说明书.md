## 目标、范围与非目标

当前用户在页面可以看到分析过程，刷新后却缺少对应内容；业务请求轨迹主要记录 Master 的委派工具，没有完整反映子 Agent 业务调用，用量也缺少写入链路。

本次目标是让一次业务请求具有可保存、可关联、可解释的结果：会话消息保留正文与实际模型思考，请求轨迹保留分析结果、业务工具和模型用量。未来任务看板可以利用请求摘要了解大致执行了什么、结果来自哪里。

本次包含：

- 分清问题改写、意图识别的分析结果与 Master 实际模型思考，分别保存和展示。
- 补齐 Master 及子 Agent 本分段的实际业务工具执行摘要、模型用量和已知数据来源。
- 在现有结果保存入口汇总；异常或取消没有正常结果时，在现有实际退出收尾保存已知摘要。
- 历史按业务 Run 组合两表数据，完成最低限度的刷新后展示。

明确延期：任务看板、实时任务进度持久化、逐条重放全部 SSE、供应商 HTTP 调用审计与计费、全部子 Agent 思考展示、历史缺失数据回填。取消时未完成的模型正文和思考不在本次补存范围；现有取消状态提示继续保留。

保持现有能力边界：一个框架 HarnessAgent、本地父子协同、整批审批收口与恢复、取消后的真实退出确认、可信会话归属和现有观测接入。问题改写和意图识别仍可直接执行 Model，不强制接入 Fons4AI Harness。

## 场景与业务流程

| 场景 | 触发与主要步骤 | 用户可观察结果 |
| --- | --- | --- |
| 普通请求 | 用户发送消息；规则/缓存或分析模型处理；Master 委派；当前分段结束并保存 | 正文与分析结果均可查看，刷新后仍存在；工具摘要包含子节点实际业务调用 |
| 多项审批 | 子 Agent 产生审批；本阶段全部安全收口；保存消息、摘要和票证；执行权交接 | 仍按整批提交；请求摘要只展示一次；未批准工具不显示为已执行 |
| 审批恢复 | 用户提交整批决定，启动新业务 Run，恢复原生状态 | 原 Run 保留原分段数据，新 Run 保存新增调用；不会重复累计旧用量 |
| 取消或失败 | 执行中取消、模型失败或工具异常；等待受管执行真实退出 | 已知分析/工具/用量可保存；缺失用量有明确说明；取消提示继续保留 |
| 历史读取 | 用户刷新或进入已有会话；服务端校验归属并关联请求轨迹 | 同一 Run 的多条正文、媒体、审批卡不重复展示请求摘要；旧数据缺失不伪造 |

这里的“分段结束”包括正常结束和审批等待，不等于用户的差旅业务目标已经全部完成。失败、拒绝、超时也不能展示成业务成功。

## 业务规则与数据口径

### 1. 会话展示与请求摘要

- 正文、人工交互消息、取消状态提示属于会话消息；问题改写、意图结果和执行概况属于请求轨迹。
- “正在识别需求”等是应用发布的过程提示，不是模型推理内容。刷新后展示分析结果即可，不要求还原每条进度提示。
- Master 只有实际产生模型思考时才保存和展示；无思考时为空。子 Agent 的思考不能无身份地拼到 Master 下。
- 一个 Run 多条审批/媒体消息共享一份请求摘要；相同 Master 思考也不应被复制展示成多次独立思考。

### 2. 请求与分段归属

- 业务 `runId` 标识本次请求轨迹；`pipelineRunId` 标识外层执行，不混用。
- 一次审批暂停可包含多个待决定工具，仍属于原 Run 的一个分段结果。
- 恢复创建新 Run，并关联 `originRunId`。历史分析仍保留在原 Run，跳过的分析步骤不生成一份虚假新结果。

### 3. 工具与供应商

- “已执行业务工具”表示已进入业务工具实现。待审批、权限拒绝、SDK 参数校验拦截及业务防重短路均不能计作再次执行。
- 实际进入后返回业务失败的工具仍属于已执行；工具执行成功不等于查到候选或完成差旅目标。
- 摘要名称按工具名去重；执行明细按调用尝试保留。例如同一查询实际调用两次，名称只列一次，明细两条；其中一条被防重拦截则标为跳过。
- SDK 委派、待办、文件等内部工具可以保留在执行明细，但不混入业务工具集合。未知类别不能仅凭“名称不是 agent_ 开头”判断为业务工具。
- 供应商/数据来源只能来自实际业务结果或有证据的执行适配，不从模型描述推断。无来源时为空；来源标识不等于已经审计了 HTTP 次数、计费或网络重试。

### 4. Token 用量

统计单位是供应商通过模型适配返回的 Token，表示本次请求的已知用量，不表示费用。

- 计算范围：本次实际执行的问题改写、意图识别、Master 和子 Agent 模型调用。
- 每次模型调用取最后一个非空 usage；父节点重复转发同一事件不再加一次。独立发起的新调用/重试分别计数，供应商内部不可见重试不推测。
- 一次调用若输入 200、输出 100、缓存输入 50，总量为 300，不能将缓存再次加为 350。
- 规则或缓存命中、恢复跳过分析不产生本次模型消耗，不能把缓存来源 Run 的用量带过来。
- 没有任何模型调用是已知零；存在调用但全无 usage 为未知；部分调用有 usage 时保存已知小计并标记不完整。
- 示例：改写 100、意图 150、Master 300、子 A 400、子 B 250，总量 1200。Master 流内累计片段为 100/200/300，只取 300。若子 B 缺失，则已知小计 950，完整性为否，不能当成请求完整消耗。

### 5. 收尾与失败

正常/审批结果沿已有结果事务保存；实际退出后补齐摘要，防止取消后迟到的已准入工具被遗漏。执行未退出时不得交还会话占用或开放审批。

摘要保存失败时，不能发布已完成的最终交接；数据库占用清理和票证开放回滚。不会为了重试保存而重新执行模型、工具或业务副作用。重复读取、重复订阅同一收尾结果不追加多份消息/明细。

## 验收与约束

| 编号 | 前提与动作 | 可判定结果 |
| --- | --- | --- |
| AC-1 | 普通请求实际经过改写和意图识别，完成后刷新 | 两项分析结果可读；来自请求轨迹，不依赖浏览器内存，也不伪装成 Master 模型思考 |
| AC-2 | Master 实际输出一段思考并结束；另验无思考请求及多卡审批 | 有思考时消息字段与展示内容一致；无思考不伪造；同一 Run 不重复显示多份相同思考 |
| AC-3 | Master 委派子 Agent，子节点实际执行查询；包含失败、待审批和防重短路分支 | 业务工具集合含实际查询和失败调用；无纯委派/内部工具；待审批、拒绝、拦截不误计执行 |
| AC-4 | 获得模型 usage、流式累计值及缺失 usage | 按上述 1200/950 例子可核算；无重复相加；未知与零、小计与完整总量可区分 |
| AC-5 | 工具成功结果有明确供应商来源；另有失败或无来源工具 | 执行摘要含 Agent、工具、状态及已知来源；未知为空；不保存完整参数、响应或凭据 |
| AC-6 | 同批两项审批后恢复；另验模型执行中取消及工具执行中取消 | 新旧 Run 分开统计并可关联；取消等待真实退出；已知摘要和取消提示刷新后可读，票证不会被重复开放 |
| AC-7 | 关闭观测，分别发起普通/子 Agent 请求 | 业务保存仍工作；无新增根采集器、第二个 HarnessAgent 或模型代理依赖 |
| AC-8 | 分页读取旧记录、多消息 Run，以及越权读取 | 每个当前加载 Run 只显示一份请求摘要；缺失数据不宣称为零；其他用户会话仍拒绝访问 |

沿用 [工程约定](../../../wiki/工程约定.md)：不新增/运行单元测试；后端由用户启动/重启；MySQL 只用 MCP 只读核验，DDL/DML 由用户执行。真实模型、只读工具和审批的最小验收在用户确认实施并通知重启就绪后开展，不扩展到预订、支付或无关供应商调用。
